# Проверка и релиз

## Проверка партии и кандидата

1. Прочитать `AGENTS.md`, `migration/PLAN.md`, `migration/INVENTORY.md`, `migration/STATUS.md` и реестры. Использовать готовые средства проверки и браузер; не объявлять непроведённую проверку успешной.
2. Сверить реестры с деревом `site/`: каждый captured/verified имеет файл, каждый файл имеет происхождение или служебное назначение. Проверить отсутствие query-имён, коллизий, PHP, секретов, временных загрузок и посторонних артефактов в публикуемом наборе.
3. Для каждой страницы сравнить весь основной текст источника и копии, нормализуя только пробелы и переносы. Проверить начало, середину и конец длинных статей, библиографию, подписи, русские и башкирские буквы. Разницу объяснить; не использовать одинаковые размеры HTML как доказательство полноты.
4. Для каждого ресурса сверить MIME, ненулевой размер, SHA-256 и успешное открытие. Для CSS, изменённого при локализации путей, сохранить исходный хеш и проверить конечные зависимости. Галерею сверить по всем категориям/страницам/оригиналам и подписям, а не по нескольким превью.
5. Готовым link checker или эквивалентной проверкой охватить все внутренние href/src/srcset, CSS url/import, фрагменты и регистр путей. Каждая цель должна существовать под `/ufalit/`; HTTP 200 с подставленной главной страницей не считается верной целью.
6. Поднять локальную проверку через готовый статический сервер с префиксом `/ufalit/` (например, serve родительского каталога, содержащего папку `ufalit` с копией `site/`). Проверка только из корня `/` недостаточна. Открыть главную и все типы вложенных страниц на широком и узком экране.
7. Заблокировать исходный домен в браузере и пройти локальные тексты, изображения, документы и галерею. По Network проверить отсутствие запросов к Joomla для их работы. Внешние карты, видео и другие зависимости проверить отдельно и включить в отчёт. Не обещать полную автономность внешнего видео.
8. Для каждого видимого интерактивного элемента подтвердить действие или понятную статическую замену. Проверить отсутствие сломанных форм и переходов на PHP. Старые входящие query-URL и неизбежные отличия указать явно.
9. Обновить `migration/QA.md`: дата, SHA кандидата/партии, инструменты, точные действия, числа из реестров, результаты по всему охвату, evidence и ограничения. `verified` присваивать только после соответствующих проверок. Непроверенное пометить отдельно.
10. Кандидат готов при закрытой очереди, отсутствии необъяснённых пропусков и сломанных внутренних ссылок, сохранности полного текста и локальных файлов. Существенные исключения требуют решения пользователя. Проверить актуальные лимиты GitHub/Pages и общий размер; при превышении предложить конкретный вариант до релиза, не удалять файлы молча.

## Публикация после отдельного поручения

1. Убедиться, что пользователь поручил опубликовать подготовленный кандидат. Если разрешения нет, представить ссылку на commit/SHA, QA и ограничения, завершив подготовку без включения Pages.
2. Повторно проверить default branch, состояние Pages, целевой URL, актуальные официальные инструкции и SHA кандидата. Если кандидат изменился, выполнить затронутые проверки заново. DNS и собственный домен настраивать только по отдельному поручению.
3. Создать/обновить `gh-pages` обычным коммитом без force push. В корень перенести только содержимое `site/`; добавить `.nojekyll`. Удаление устаревших файлов ограничить прежним публикуемым набором. Сохранить SHA предыдущей публикации и SHA источника релиза в QA.
4. Настроить Pages: `Deploy from a branch`, ветка `gh-pages`, `/ (root)`. Не разрабатывать сборку или workflow для обычных статических файлов. Если подключённый GitHub не умеет настройки Pages, использовать доступный штатный интерфейс; если он недоступен, назвать оставшийся шаг, а не утверждать, что сайт опубликован.
5. Проверить завершение деплоя и настоящий URL GitHub Pages: HTTPS, главная, вложенные статьи, галерея, документы, пути CSS/изображений и 404. Сверить опубликованные материалы с кандидатом и повторить проверку без исходного домена. Публичный URL без проверки не доказывает успешный релиз.
6. Записать итог в QA и STATUS: URL, SHA, дата, результат и ограничения. Для отката использовать revert релизного коммита с повторной проверкой; при первой публикации при необходимости отключить Pages. Joomla не удалять.
